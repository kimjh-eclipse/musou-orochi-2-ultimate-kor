# 아카이브·압축·문자열

이 문서는 BLJM61084에서 확인한 구조를 설명합니다. 게임 아카이브는 주로 **빅 엔디언**, 배포용 팩·백업은 **리틀 엔디언**입니다. 두 계층을 혼동하면 크기·포인터가 모두 잘못 해석됩니다.

## LINKDATA.IDX

`LINKDATA.IDX`는 1,198,592바이트이며 32바이트 레코드 37,456개로 구성됩니다. 개발 파서의 레코드 선언은 Python `struct.Struct(">QQQQ")`입니다.

| 레코드 내 위치 | 형식 | 의미 |
|---|---|---|
| `+0x00` | u64 BE | BIN 내 시작 오프셋 |
| `+0x08` | u64 BE | 압축 해제 후 크기 |
| `+0x10` | u64 BE | 저장된 크기 |
| `+0x18` | u64 BE | 압축 플래그; 파서는 0이 아니면 래퍼 해제 |

파서는 BIN의 `offset`부터 `stored_size`만큼 읽습니다. 압축되지 않은 항목과 압축 항목을 구분해야 하며, 모든 항목을 zlib로 간주하면 안 됩니다.

패치의 기본 전략은 **리소스 시작 위치와 BIN 총길이를 유지**하는 것입니다. 수정 데이터를 다시 압축한 뒤 원래 슬롯에 넣고, 필요한 IDX 크기 필드만 갱신합니다. 순서와 경계가 확인된 항목의 슬롯 용량은 다음 항목 시작 위치와의 차이로 계산할 수 있습니다.

```python
capacity = next_entry.offset - entry.offset
assert capacity >= entry.stored_size
assert len(new_stored_data) <= capacity
```

위 식은 모든 IDX 항목에 무조건 적용하는 규칙이 아닙니다. 마지막 항목, 빈 항목, 비정상 순서 등은 별도 경계 검사가 필요합니다. 슬롯을 넘으면 빌드를 중단하며 다음 리소스를 덮어쓰지 않습니다.

## PS3 압축 래퍼

압축 데이터는 zlib 스트림 하나가 아니라 다음 래퍼에 들어 있습니다.

| 위치 | 형식 | 내용 |
|---|---|---|
| `0x00` | u32 BE | 버전 `0x00010000` |
| `0x04` | u32 BE | 블록 수 N |
| `0x08` | u32 BE | 전체 압축 해제 크기 |
| `0x0C` | u32 BE × N | 블록별 저장 레코드 크기 |
| 정렬 후 | 반복 블록 | u32 BE payload 길이 + zlib payload |

첫 블록은 `align(12 + 4*N, 0x80)`에서 시작합니다. 각 블록을 읽은 다음에는 크기 테이블 기준 레코드 끝을 `0x80` 경계에 맞춰 다음 블록으로 이동합니다. 테이블 크기에는 최소한 길이 필드 4바이트와 payload가 들어가야 합니다.

빌더는 비압축 데이터를 `0x10000`바이트 단위로 나눠 zlib level 9로 압축합니다. 중요한 불변식은 다음과 같습니다.

```text
decompress(compress(new_payload)) == new_payload
decompressed_length == IDX.unpacked_size
compressed_length <= allocated_slot_capacity
```

이는 **압축 해제 결과의 완전 일치**입니다. 같은 내용을 재압축했을 때 원본 압축 바이트까지 같다는 뜻은 아닙니다. 라이브러리·설정 차이로 압축 바이트가 달라질 수 있으므로 두 검증을 구분합니다.

## LX 리소스와 번들

문자열은 직접 `LX`로 시작하는 리소스 또는 여러 LX 섹션을 포함하는 번들에 존재합니다. 현재 파서가 인식하는 번들은 u32 BE 섹션 수와 `(offset, size)` 형태의 `>II` 디스크립터를 사용합니다. 섹션 경계는 다음 섹션 시작 위치 또는 파일 끝과 함께 검증합니다.

LX 파서는 다음 필드를 사용합니다.

| 섹션 시작 기준 | 형식 | 용도 |
|---|---|---|
| `+0x00` | 2 bytes | `LX` 서명 |
| `+0x02` | u16 BE | 확인된 버전 `0x13`, `0x14` |
| `+0x08` | u16 BE | 레코드 수 |
| `+0x0A` | u16 BE | 레코드 폭 |
| `+0x0C` | u32 BE | 섹션 기준 테이블 위치 |

문자열 포인터는 각 레코드의 마지막 4바이트에 있습니다. 값의 기준점은 **파일 시작도 LX 섹션 시작도 아닌 테이블 시작**입니다.

```python
table = section_base + read_u32be(section_base + 12)
pointer_field = table + record_index * record_width + record_width - 4
relative = read_u32be(pointer_field)
string_offset = table + relative
```

`0xFFFFFFFF`는 문자열 없음으로 처리합니다. 포인터·레코드가 섹션 경계를 벗어나면 오류로 보고, NUL 종결 문자열의 원시 바이트와 디코딩 결과를 함께 보관합니다. CP932 디코딩 실패를 조용히 지워 버리면 원본이 손실되므로 invalid 표시와 raw hex를 남깁니다.

## 문자열 풀 재구성

번역문 길이는 원문과 다를 수 있습니다. 각 문자열을 제자리에서 무조건 덮는 대신, 해당 섹션 안에서 검증된 문자열 풀을 재구성하고 레코드 포인터를 갱신합니다.

1. 레코드 수·폭·포인터 위치와 원문 바이트를 수집합니다.
2. 가장 이른 문자열 위치부터 섹션 끝까지 사용 영역을 계산합니다.
3. 알려진 문자열 외의 비영(非零) 데이터가 있으면 중단합니다. 모르는 데이터를 여유 공간으로 취급하지 않습니다.
4. 원시 바이트가 같은 문자열은 공유하고, 각 문자열에 NUL을 붙입니다.
5. 재구성한 풀의 크기가 기존 용량 이내인지 확인합니다.
6. 테이블 기준 상대 포인터를 다시 기록합니다. 나머지 영역과 전체 섹션 길이는 유지합니다.

변경하지 않은 문자열은 디코딩 후 재인코딩하는 대신 원시 바이트를 보존합니다. 색상·제어 코드와 `%s`, `%w` 같은 토큰은 [인코딩 문서](font-text.md)의 규칙에 따라 검증합니다.

## 아카이브 재삽입의 검증 기준

- IDX 레코드 수와 BIN 총길이가 변하지 않을 것.
- 허용된 항목 외의 데이터와 인덱스 레코드가 바뀌지 않을 것.
- 압축 후 슬롯 용량을 넘지 않을 것.
- 최종 BIN에서 다시 추출한 리소스가 빌드한 payload와 같을 것.
- LX 포인터, 레코드 식별자, 제어 토큰, NUL 경계가 유효할 것.

분석 기준 구현은 개발 도구의 `linkdata_tool.py`, `jp_text_catalog.py`, 문자열 빌더입니다. 이 분석 도구 전체가 공개 저장소에 포함되어 있는 것은 아닙니다. [공개 범위와 재현 조건](validation.md)을 참고하세요.
