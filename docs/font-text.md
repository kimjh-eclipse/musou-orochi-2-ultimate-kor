# 한글 인코딩·폰트

## UTF-8 문자열을 넣는 패치가 아니다

일본판 텍스트 엔진의 CP932 코드와 글리프 참조를 유지하면서, 선택한 대체 코드의 폰트 셀을 한글로 바꾸는 방식입니다. 번역문을 UTF-8이나 CP949로 그대로 저장하지 않습니다.

```text
한국어 번역문 → 문자별 매핑 → CP932 대체 코드 바이트
                                ↓
                       엔진의 기존 글리프 참조
                                ↓
                       해당 셀의 한글 비트맵
```

매핑에는 한국어 문자, 원래 문자(donor), CP932 바이트, 글리프 인덱스와 아틀라스 좌표를 함께 저장합니다. 현재 번역 빌드에는 한글 1,270자 매핑이 사용됩니다. 이는 유니코드 한글 전체를 지원하는 폰트나 한글 입력기 구현을 의미하지 않습니다.

## 대체 코드 선택과 매핑 안정성

스캔한 문자열에서 쓰지 않는 후보 코드를 골라 한글에 배정합니다. 이미 배정한 글자를 재배정하면 기존 번역 전체의 표시가 바뀌므로 매핑을 고정하고 필요한 문자만 추가합니다.

검사 항목은 한글 중복, 코드 중복, 글리프 셀 중복, 번역문에서 요구하는 문자 누락입니다. 분석된 LX에서 사용되지 않는다는 사실만으로 **미해석 데이터에서도 미사용이라고 보장할 수는 없습니다.** 새 영역을 조사할 때 충돌 여부를 다시 확인해야 합니다.

초기 1수준 코드의 좌표 계산에는 `ordinal(code)-844`와 64열 배치가 사용됐습니다. 이 계산을 JIS 2수준이나 다른 코드 영역에 그대로 확대 적용하면 안 됩니다. 검증된 매핑 파일의 좌표를 기준으로 사용합니다.

## 실제 폰트 아틀라스 구조

대상은 LINKDATA entry 42입니다.

| 항목 | 확인한 값 |
|---|---|
| 실제 해석 크기 | **2048 × 4096** |
| 글리프 셀 | **32 × 32**, 가로 64셀 |
| 압축 | BC3 / DXT5 |
| 픽셀 데이터 시작 | `0x38` |
| 블록 | 4 × 4픽셀, 16바이트 |

이전 문서의 **4096×2048, 32×16 두 면을 합성한다는 설명은 잘못된 분석**입니다. 잘못된 가로 pitch로 읽으면서 한 글자의 4행 블록 띠가 두 위치로 나뉘어 보였던 것입니다. 올바른 해석은 한 개의 32×32 글리프이며, 이 수정은 해당 리소스에 대한 검증 결과입니다. 모든 G1T에 같은 치수를 적용하지 않습니다.

셀 `(x, y)` 안의 블록 `(bx, by)`의 위치는 다음과 같습니다.

```python
block_offset = 0x38 + ((y // 4 + by) * (2048 // 4) + x // 4 + bx) * 16
# bx, by: 0..7
```

## 렌더링·BC3 기록

한글을 32×32 마스크에 직접 렌더링하고 획의 바운딩 박스를 확인해 중앙에 배치합니다. 개발 렌더러는 글자 잉크가 최대 30×30 안에 들어오도록 검사해 여백을 확보합니다. 글자를 강제로 가로·세로로 늘여 맞추는 방식이 아닙니다.

BC3 블록의 앞 8바이트는 알파, 뒤 8바이트는 색 정보입니다. 폰트 패치는 필요한 셀의 알파 블록만 갱신하고 색 블록과 이웃 셀은 보존합니다. 알파 양자화가 들어가므로 원래 마스크와 픽셀 값이 모두 같지는 않습니다. 인코딩 후 다시 디코딩해 획·여백·알파 오차를 검사합니다.

필수 회귀 검증은 기존 한글 셀 보존, 대상 셀 밖의 바이트 동일, 이웃 글리프 동일, 압축 해제 결과 동일, 원래 슬롯 용량 준수입니다. 보기 좋은 미리보기만으로 통과시키지 않습니다.

## 이름 뒤 별표·특수문자가 나온 이유

전투의 일부 이름 필드는 2바이트 경계로 문자를 처리하는 특성이 있습니다. 이런 필드에 ASCII 공백 `20`이 들어가면 뒤쪽 문자의 바이트 짝이 어긋납니다. 결과적으로 `*`나 엉뚱한 특수문자가 보일 수 있습니다.

실제로 조사한 이름 바이트의 예입니다.

```text
수정 전: 9B F2 E2 5C 20 99 81 89 82
2바이트 분리: 9BF2 / E25C / 2099 / 8189 / 82
                                         ↑ 8189는 CP932에서 ♂

수정 후: 9B F2 E2 5C 81 40 99 81 89 82
2바이트 분리: 9BF2 / E25C / 8140 / 9981 / 8982
                              ↑ 전각 공백
```

별표만 삭제하는 것으로는 경계 오류를 해결할 수 없습니다. 해당 이름·읽기 필드에서는 ASCII 공백을 전각 공백으로, 출력 가능한 ASCII를 필요한 전각 문자로 정규화했습니다. 이 규칙은 **확인된 이름 필드 전용**입니다. 일반 문장의 `%` 토큰·제어 코드까지 일괄 전각화하면 게임 동작이 깨질 수 있습니다.

조사는 무장 이름 1,900개와 읽기 1,900개 테이블로 확대했고, 이름·읽기 1,254행 및 같은 사용처 1행을 수정했습니다. 정적 경계 검사는 통과했지만 모든 전투·대화 화면의 실제 표시가 확인된 것은 아닙니다.

## 제어 코드와 문장 길이

번역 전후에 다음을 비교합니다.

- 색상·아이콘·줄바꿈 등 제어 시퀀스의 유효성.
- `%s`, `%w` 등 치환 토큰의 수와 순서.
- 원문과 번역 레코드의 식별자 연결.
- NUL 종결과 인코딩 가능한 문자 집합.
- 문자열 풀 용량과 화면별 길이 제한.

특정 빌드의 26셀 줄 길이 제한은 그 화면을 위한 작성 규칙이지 게임 전체의 픽셀 폭 보증이 아닙니다. 선택 시 확대, 테두리, 가변폭 문자, 두 줄 이상의 안내문은 실제 화면 확인이 필요합니다.

키보드 왼쪽의 분류·완료 버튼을 번역한 것과 한글 키보드를 구현하는 것은 별개입니다. 현재 문자 입력 그리드는 일본어이며 한글 IME를 추가하지 않았습니다.
